# NYC Job Search Pipeline Agent

See [job_search_agent_architecture.md](job_search_agent_architecture.md) for the full design.

## Repo layout

- `config/companies.yaml` — tier-list companies mapped to ATS type + Track (A/B/C). Populated by the company ATS audit (build order step 1).
- `.claude/agents/` — subagent definitions for each pipeline stage (ats-discovery, linkedin-discovery, company-monitor, fit-scorer, resume-tailor, form-filler).
- `src/db/schema.sql` — SQLite schema (postings, filter_results, scores, tailored, applications, company_page_hashes, company_monitor_alerts).
- `src/discovery/`, `src/filter/`, `src/score/`, `src/tailor/`, `src/formfill/`, `src/dashboard/` — pipeline stage implementations, filled in per the build order.
- `resumes/` — existing per-company LaTeX resume bases (baseline tailoring inputs).
- `data/` — local SQLite DB and generated artifacts (gitignored).

## Running discovery

```
pip install -r requirements-dev.txt   # includes pytest
python3 -m pytest tests/              # unit tests (no network)
python3 -m src.discovery.run_track_a_simple    # live poll: Greenhouse + Ashby companies (39)
python3 -m src.discovery.run_track_a_workday   # live poll: Workday companies (17, paginated)
python3 -m src.discovery.run_track_c_monitor   # live check: hash-diff monitor, 32 custom/protected companies
python3 -m src.discovery.run_track_b_linkedin  # live scrape: Apify LinkedIn jobs actor, needs APIFY_TOKEN
python3 -m src.filter.run_filter               # filter postings: NYC + full-time + SWE/AI title, no LLM
python3 -m src.score.run_score                 # LLM fit score (Haiku 4.5) for filter-passed postings, needs ANTHROPIC_API_KEY
python3 -m src.tailor.run_tailor                # tailor resume + outreach draft for score>=8 postings, needs ANTHROPIC_API_KEY + pdflatex
python3 -m src.tailor.run_review_list           # markdown review list for scored postings below the tailor threshold
```

The Track A runners are idempotent — re-running against the same DB only inserts postings not already seen (deduped by URL hash). The Workday runner is slower by design: it paginates in steps of 20 with a delay between pages and retries an empty page before treating it as terminal, per the architecture doc. The Track C runner is a monitor, not a discovery source -- it writes to `company_page_hashes` every run and only writes to `company_monitor_alerts` (a separate table from `postings`) when a hash change looks job-shaped; see `src/discovery/company_monitor.py`'s module docstring for the full design. The Track B runner needs an `APIFY_TOKEN` (in a `.env` file in the repo root, or exported) -- it fails with a clear message rather than silently skipping if the token is missing.

- Step 1 (company ATS audit) — done, see `config/companies.yaml` (88 companies, 56 Track A / 32 Track C).
- Step 2 (Track A discovery) — done, all three sources:
  - Greenhouse + Ashby: `src/discovery/{greenhouse,ashby}.py` + `run_track_a_simple.py`, 39 companies.
  - Workday: `src/discovery/workday.py` + `run_track_a_workday.py`, 17 companies, paginated POST with empty-page retry. Two undocumented Workday quirks drove the pagination logic (see the module docstring): the `total` field goes unreliable near the end of a board, and an out-of-range offset silently re-serves page 1 instead of coming back empty -- so termination is based on partial-page-size, not on `total` or on emptiness alone.
  - Shared `normalize.py` / `store.py` / `config.py` across all three sources -- no per-source dedup logic duplicated.
  - Tested live end-to-end for both runners (fresh-DB pass + idempotency-check pass), not just unit tests against fixtures.
- Track C (company-monitor hash-diffing) — done: `src/discovery/company_monitor.py` + `run_track_c_monitor.py`, 32 companies. Hashes normalized visible text (not raw HTML, not embedded JS state -- tested and rejected, see module docstring for why), diffs on a hash change and keyword-gates the diff before writing a low-confidence "worth a look" alert to its own table, never straight into `postings`. First run per company seeds a baseline only (no alert). Live-tested end-to-end (fresh pass + repeat pass): 29/32 companies fetch successfully, 3 are bot-blocked (Tesla, Citadel Securities, Meta -- tracked via `consecutive_fetch_failures`, not treated as a content change), 10 flagged `low_confidence` (client-rendered shells where hash-diffing is a weak signal), and one live noise source found and fixed mid-build (a per-request hex token on Phenom-People-backed sites that changed on every fetch regardless of content -- now scrubbed).
- Track B (LinkedIn via Apify) — done: `src/discovery/linkedin.py` + `run_track_b_linkedin.py`, built against the documented input/output schema of the `curious_coder/linkedin-jobs-scraper` actor (checked live via its public docs, not guessed). Reuses `normalize.py`/`store.py` exactly as Track A/C do -- `normalize_linkedin_job` is the only new mapping, tagged `source: "linkedin"`. Adaptive widening: if a search returns fewer than 5 results it escalates through a 4-step ladder (broaden keywords, then radius, then both) before giving up, returning the best attempt found rather than nothing, same retry-with-honest-reporting shape as the Track A/C retry logic. 17 unit tests cover the Apify call shape and every widening branch against mocked responses. Two real bugs surfaced only by the live pass, both fixed and covered by regression tests: (1) Apify's run-sync endpoint returned HTTP 201 (not 200) for a run that actually executed rather than reusing a cached result -- the status check only accepted exactly 200 and treated a perfectly valid response as an error; (2) LinkedIn's `link` URL carries per-search tracking params (`refId`/`trackingId`/`position`) that regenerate on every fresh search of the same query, so hashing the raw link made every re-fetch of an already-seen posting look "new" -- dedup now keys off the stable `id` field instead. Live-verified end-to-end after both fixes: first pass inserted 50 new postings, second pass against the same DB found all 50 already seen, 0 new -- clean idempotency.
- Filter stage — done: `src/filter/rules.py` + `run_filter.py`, four cheap deterministic rules, no LLM calls, checked in order (location → employment_type → title_keyword → title_seniority) so a posting failing several is reported under the first one, not double-counted. Every rule was shaped against real data pulled by the discovery runners, not assumed:
  - **Location**: a strict "New York, NY" substring match would have missed most genuinely-NYC postings -- Greenhouse spells the state out ("New York, New York, United States"), Ashby/Workday often give just the bare city ("New York") with no state at all. Confirmed with you before broadening: now splits multi-location strings on `;` and matches if any entry's city (the text before its first comma) is exactly "New York" -- this also correctly rejects state-reference false positives ("Albany, New York") and treats a posting listing "New York, NY" alongside a separate "Remote" entry as a real NYC opportunity, not a remote-only one (found 29 real postings shaped exactly like that).
  - **Employment type**: only Ashby (982/982) and LinkedIn (50/50) postings carry a structured `employmentType` field live; Greenhouse and Workday's list endpoints expose none at all (0/5833, 0/23) -- defaulting those to "excluded" would have gutted most of Track A for a data-availability reason, not a real employment-type mismatch. Uses the structured field when present, falls back to a title keyword heuristic (catches "... Intern", "... Contract", etc.) when absent, and only then defaults to full-time.
  - **Title**: matches a keyword set scoped to what was asked (Software Engineer/SWE/Software Developer/Backend/Full Stack/Frontend/AI Engineer/Machine Learning Engineer + close variants), word-boundary matched so short tokens like "swe" can't false-positive inside unrelated words ("answered"). Excludes Senior/Sr./Staff/Principal/Manager, plus Lead -- added after reviewing real results showed ~18% of what passed was "Lead Software Engineer"-type titles (mostly Capital One), which reads as senior-tier in practice and is out of scope at ~22 months of experience. Also picked up narrow AI/ML-signal additions after reviewing 25 excluded Data/Research Engineer postings: Deep Learning Engineer, Deep Learning Research Engineer, and bare "Research Engineer" (HRT/Jump Trading-style research-engineer roles skew quant/ML even without the literal word "AI", and this phrase alone also covers "AI Research Engineer" and "Machine Learning Research Engineer" as substrings). Deliberately did NOT add bare "Data Engineer" -- reviewed samples showed it pulls in far more data-infra/pipeline noise (Point72's Data Engineer cluster, Stripe's "Data Analyst") than real ML matches; verified live that Point72's Data Engineer roles stayed excluded after the change while their "Research Engineer, Knowledge Graph Intelligence" role correctly started passing.
  - **Dedup**: a new `filter_results` table (posting_id PK) records pass/fail + reason per posting; a posting already in it, passed or excluded, is never re-evaluated.
  - 52 unit tests against fixtures grounded in the real formats found, then live-run against the full postings table from all three discovery tracks (repeated after each rule change), then a second pass each time confirming 0 newly evaluated / all already filtered. Current result: **117 passed** of 21,327 (19,961 excluded by location, 1,158 by title keyword, 60 by title seniority, 31 by employment type). Of the 23 Data/Research Engineer postings that reached the title check, 10 now pass (all HRT/Jump Trading/PDT Partners/Tower Research AI-or-research-flavored roles) and 13 stay excluded (Point72's Data Engineer cluster, Jane Street/BlackRock/Blackstone/Morgan Stanley/Capital One Data Engineer variants, Stripe's Data Analyst) -- confirmed the narrower keywords pulled in the intended roles without reintroducing the infra/pipeline noise.
- Score stage — done: `src/score/{profile,scorer,store}.py` + `run_score.py`.
  - **Profile**: `profile.py` is a small custom parser for the Baseline resume's LaTeX macros (`\resumeSubheading`, `\resumeItem`, `\resumeProjectHeading`, `\section`) -- not a general LaTeX-to-text converter, scoped to this template specifically since all 8 resumes share the same command definitions. Renders Education/Technical Skills/Professional Experience/AI-ML Projects as clean plain text, in document order, with contact info excluded (not relevant to fit). Baseline was picked over a company-tailored resume deliberately -- diffing it against a couple of variants (Virtu, Optiver) showed they're the same underlying jobs/bullets just re-worded per company, not different experience.
  - **Scorer**: Haiku 4.5, called with a forced tool-use (`submit_fit_score`, `{score: 1-10, reasoning: string}`) rather than asking for free text and regex-parsing it -- deterministic to extract, and `parse_tool_response` rejects an out-of-range score or missing reasoning as an error rather than silently storing garbage. Job descriptions aren't uniformly available -- Greenhouse/Ashby/LinkedIn carry one, Workday's `cxs/jobs` list endpoint exposes none at all -- so the prompt says so explicitly rather than silently omitting the field. The system prompt frames the actual agentic ask from the doc: judge fit holistically rather than trusting title-keyword-matched-therefore-good-fit, since the Filter stage already did the hard keyword filtering and this stage's whole purpose is to catch what that can't (a superficially-matching title that's really a different job in practice, or a seniority mismatch the description implies but the title doesn't state).
  - **Dedup**: only scores postings that passed `filter_results` and don't already have a `scores` row -- mirrors `filter/store.py`'s shape exactly.
  - 30 unit tests (7 profile extraction against a synthetic fixture resume, 23 scorer/prompt/tool-parsing against a mocked Anthropic client), no real API calls in the test suite, then live-run against all 117 filter-passed postings with a second pass confirming 0 newly scored / all already scored. Score distribution: 9:1, 8:25, 7:37, 6:24, 5:4, 4:13, 3:11, 2:2 (mean 6.2). Hand-checked a sample of the reasoning against the actual postings -- consistently specific and grounded in real details on both sides (candidate's actual employers/stack/experience length vs. the posting's actual stated requirements), no generic filler or hallucinated claims found. One case validated the agentic feature directly: BlackRock's "Rust, AI Engineer, Director" posting passed the Filter stage (its title contains "AI Engineer" and "Director" was never in the keyword-based seniority exclusion list), but Haiku correctly scored it 3/10, citing the Director-level seniority mismatch against the candidate's ~1 year of experience -- exactly the kind of judgment call the doc's design intends this stage to make that a keyword list can't.
- Tailor stage — code done, live compile run pending a local LaTeX toolchain: `src/tailor/{resume_tailor,store,review}.py` + `run_tailor.py` + `run_review_list.py`. Threshold: score >= 8 auto-tailors a resume + outreach draft (~26 of the 117 filter-passed postings right now); everything scored but below that goes into a markdown review list instead (company/title/score/reasoning/link, sorted by score descending) so it's still reviewable by hand.
  - No "resume-tailor skill" exists anywhere on this machine to reuse verbatim -- checked, and like the Portfolio Agent Apify code the architecture doc referenced, this turned out to be aspirational rather than present. Built the tailoring approach from scratch instead.
  - **Bullets, not the whole file, are what the LLM touches.** `src/common/latex.py` (pulled out of `score/profile.py`, now shared by both stages) locates every `\resumeItem{...}` call's exact position in the base .tex; Sonnet only ever sees and returns bullet text, never raw LaTeX syntax to author, and the response is spliced back into the *original* document at those exact positions. Considered and rejected having the LLM regenerate the whole .tex file -- one wrong brace or a "helpful" structural change would silently break the document, and there'd be no clean way to test that deterministically.
  - Instructed to preserve the original bullets' LaTeX escaping (`\%`, `\$`, `\&`), with `escape_latex_specials()` as a second, defensive pass regardless of what Sonnet actually returns.
  - Base resume selection prefers an existing company-tailored file (e.g. `resumes/Virtu Resume.tex`) when one exists for that company, falling back to Baseline otherwise.
  - **Compile-loop**: pdflatex in nonstopmode, up to 3 attempts. Each retry is given the *real* failure -- the actual `!`-prefixed LaTeX error line, or "still N pages, must be 1" -- so it's an informed correction, not a blind re-roll. A posting that still fails after 3 attempts is recorded with `status='failed'` (not silently dropped, and not retried forever on rerun either -- same "never re-process" dedup shape as every other stage).
  - **Dedup**: `tailored` table extended with `status`/`attempts`/`failure_reason` columns; a posting already in it, tailored or failed, is skipped on rerun.
  - 62 unit tests (24 for the tailoring/splice/compile-loop logic against a synthetic fixture resume with pdflatex and the Anthropic client both mocked, 11 for the shared LaTeX brace-matcher now that it's tested directly, 15 for the review-list query/render, plus the moved description-extraction tests), all fixture/mock-based, no real compiles or API calls.
  - **Live run blocked**: no LaTeX toolchain exists on this machine at all (checked -- `pdflatex` isn't installed). Homebrew is available; asked and you picked BasicTeX. The cask installer requires an interactive `sudo` password prompt to run its pkg installer, which this automated session structurally cannot supply (no TTY, and no passwordless sudo configured) -- `brew install --cask basictex` needs to be run manually in an actual terminal before the live tailoring pass (and hand-checking the generated PDFs) can happen. The review-list half needs no LaTeX or extra tooling and is unaffected.
