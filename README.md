# NYC Job Search Pipeline Agent

See [job_search_agent_architecture.md](job_search_agent_architecture.md) for the full design.

## Repo layout

- `config/companies.yaml` — tier-list companies mapped to ATS type + Track (A/B/C). Populated by the company ATS audit (build order step 1).
- `.claude/agents/` — subagent definitions for each pipeline stage (ats-discovery, linkedin-discovery, company-monitor, fit-scorer, resume-tailor, form-filler).
- `src/db/schema.sql` — SQLite schema (postings, filter_results, scores, tailored, applications, company_page_hashes, company_monitor_alerts).
- `src/discovery/`, `src/filter/`, `src/score/`, `src/tailor/`, `src/formfill/`, `src/dashboard/` — pipeline stage implementations, filled in per the build order.
- `resumes/` — existing per-company LaTeX resume bases (baseline tailoring inputs).
- `data/` — local SQLite DB and generated artifacts (gitignored); swept after each live-verification run, treat as scratch, not storage.
- `reviewed_output/` — permanent local copies of tailored resume PDFs/.tex for manual review (gitignored, contains personal info). Unlike `data/`, never touched by cleanup -- copy anything here you need to survive past the current session.
- `.github/workflows/pipeline.yml` — the daily cron wrapper (build order step 11); see "Deployment" below.

## Running discovery

```
pip install -r requirements-dev.txt   # includes pytest
python3 -m pytest tests/              # unit tests (no network)
python3 -m src.discovery.run_track_a_simple    # live poll: Greenhouse + Ashby companies (39)
python3 -m src.discovery.run_track_a_workday   # live poll: Workday companies (17, paginated)
python3 -m src.discovery.run_track_c_monitor   # live check: hash-diff monitor, 32 custom/protected companies
python3 -m src.discovery.run_track_b_linkedin  # live scrape: Apify LinkedIn jobs actor, needs APIFY_TOKEN
python3 -m src.filter.run_filter               # filter postings: NYC + full-time + SWE/AI title, no LLM
python3 -m src.score.run_score                 # LLM fit score (Haiku 4.5) for filter-passed postings, needs ANTHROPIC_API_KEY
python3 -m src.tailor.run_tailor                # tailor resume + outreach draft for score>=8 postings, needs ANTHROPIC_API_KEY + pdflatex
python3 -m src.tailor.run_review_list           # markdown review list for scored postings below the tailor threshold
python3 -m src.dashboard.run_digest             # one combined markdown digest: ready-to-review + review list + Track C alerts
python3 -m src.dashboard.set_application_status <posting_id> <accepted|rejected>   # the accept mechanism
python3 -m src.outreach.run_outreach            # contact-specific outreach draft for tailored Track B postings, needs ANTHROPIC_API_KEY + APIFY_TOKEN
python3 -m src.notify.run_notify                # email data/dashboard.md as real HTML via SendGrid, needs SENDGRID_API_KEY
```

The Track A runners are idempotent — re-running against the same DB only inserts postings not already seen (deduped by URL hash). The Workday runner is slower by design: it paginates in steps of 20 with a delay between pages and retries an empty page before treating it as terminal, per the architecture doc. The Track C runner is a monitor, not a discovery source -- it writes to `company_page_hashes` every run and only writes to `company_monitor_alerts` (a separate table from `postings`) when a hash change looks job-shaped; see `src/discovery/company_monitor.py`'s module docstring for the full design. The Track B runner needs an `APIFY_TOKEN` (in a `.env` file in the repo root, or exported) -- it fails with a clear message rather than silently skipping if the token is missing.

## Deployment (GitHub Actions cron)

`.github/workflows/pipeline.yml` runs the whole pipeline on manual trigger (`workflow_dispatch`, or the "Run workflow" button on the Actions tab). Setup:

1. Add three repo secrets (Settings → Secrets and variables → Actions): `ANTHROPIC_API_KEY`, `APIFY_TOKEN`, and `SENDGRID_API_KEY`. No `CLAUDE_CODE_OAUTH_TOKEN` needed here -- that token only authenticates Claude Code itself (CLI/extension/`claude-code-action`), not application code making direct Messages API calls the way every stage here does, per the architecture doc's own note on the distinction. **All three secrets are now configured on this repo.** SendGrid also needs a verified sender identity (Single Sender Verification, no domain required) before it'll send anything -- see `src/notify/run_notify.py`'s `FROM_EMAIL` constant for which address that needs to be.
2. That's it -- no server, no persistent infra. `pdflatex` and Python deps install fresh each run.

**The daily `schedule:` trigger is currently disabled (commented out in the workflow).** It was enabled briefly and fired once, unprompted, before anyone decided it should -- pushing a workflow file with an active `schedule:` block to the default branch arms it immediately on GitHub's side, independent of secrets or manual triggering. No financial damage that time (it failed cleanly on a missing-secret check before any paid call), but the trigger is off until there's an explicit decision to turn it back on for real unattended daily runs.

**State persistence**: GitHub-hosted runners are ephemeral, so `data/job_pipeline.db` is restored from a `job-pipeline-db` artifact at the start of each run and re-uploaded at the end (90-day retention) -- chosen over committing the DB to git (would fight the existing "`data/` is gitignored scratch" convention and grow the repo's history unboundedly with binary diffs) or an external hosted store (real, working option, but needs new infrastructure/credentials this project doesn't otherwise require). Restoring uses `dawidd6/action-download-artifact`, not the plain `actions/download-artifact` action -- the plain one only reaches into the *current* run (or a re-run of it), not a separate earlier scheduled run, which would have meant the DB never actually persisted at all (found and fixed before the schedule trigger was ever re-enabled). `workflow_conclusion` is left unfiltered so a partially-failed run's saved progress (the save step runs on `if: always()`) is still restorable next time.

**Reading the daily digest**: `data/dashboard.md` is rendered to real HTML (`src/notify/render.py`, via Python-Markdown -- headers/bullets/bold/links as actual tags, not markdown source text pasted into an email) and emailed as the message body itself via SendGrid's REST API (`src/notify/email.py`, called directly with `requests`, no SDK dependency -- same pattern as Apify), as the pipeline's last step. No Slack delivery. `data/dashboard.md`, `data/review_list.md`, `data/tailored/*.pdf`, and `reviewed_output/*.pdf` are still also uploaded as a `daily-digest` artifact (30-day retention) each run as a durable fallback independent of whether the email actually lands. Both the `data/tailored/` and `reviewed_output/` PDFs are included in that artifact deliberately, not redundantly by accident -- `dashboard.md`'s own resume links are relative paths pointing at `../reviewed_output/{file}.pdf`, so without archiving that directory too, every resume link in a downloaded digest would be dangling (found by tracing the link-generation code against what the artifact step actually captured, not by running it).

**Cost safety default**: the cron's Score step runs with `--limit 30` rather than unlimited, since this is meant to be an unattended job with no human approving batch size before it spends real Anthropic usage -- the same reasoning behind this project's "sample before scaling up" practice during development, just applied to steady-state too. Raise or drop the flag once real daily discovery volume is well understood; lowering it later never loses anything since nothing gets re-scored once it has a `scores` row.

**Track C's exit code no longer fails the whole pipeline over expected anti-bot blocking**: `run_track_c_monitor.py` used to exit 1 on any single fetch failure, which broke a real local `&&`-chained run earlier this session even though 29/32 companies succeeded (3 are consistently bot-blocked -- Tesla, Citadel Securities, Meta). Now exits 0 unless a majority of companies failed or none were checked at all (empty config load is treated as a real error, not a clean "nothing to do" run) -- a genuinely systemic problem still fails the job, expected anti-bot noise doesn't. The workflow step no longer needs `continue-on-error: true` as a result; keeping it would have actively masked a real systemic failure instead of surfacing it.

**Isolated pdflatex dry run passed on a real Ubuntu runner**: `.github/workflows/pdflatex-dry-run.yml` (manual trigger, no secrets needed) compiled `resumes/Baseline Resume.tex` using the project's own `compile_tex_to_pdf()` -- clean success on the first attempt, no missing LaTeX packages, unlike local BasicTeX setup which needed three follow-up `tlmgr install` rounds. Good real signal, though not a substitute for a full pipeline run.

- Filter stage — done: `src/filter/rules.py` + `run_filter.py`, five cheap deterministic rules, no LLM calls, checked in order (staleness → location → employment_type → title_keyword → title_seniority) so a posting failing several is reported under the first one, not double-counted. Every rule was shaped against real data pulled by the discovery runners, not assumed:
  - **Staleness** (added after a direct question about whether Discovery pulls genuinely recent postings): LinkedIn gets a 24-hour cutoff, Greenhouse/Ashby/Workday get 14 days. The investigation that prompted this found real evergreen listings sitting unfiltered -- some over 1,000 days old (OpenAI, Palantir) -- and, worse, that Greenhouse's `posted_at` was capturing `updated_at` (a metadata-edit timestamp) instead of `first_published` -- gaps up to 1,627 days between the two on the same listing, fixed in `discovery/normalize.py`. Workday's `postedOn` is a relative string with day precision only up to 30 days, then bucketed as "Posted 30+ Days Ago"; a completely missing date (some Workday boards, e.g. Blackstone, return none at all) is treated differently from that bucket per an explicit correction -- "30+ Days Ago" IS confirmed information (excluded outright), but a missing date is zero information, not evidence of staleness, so it passes with a new `low_confidence_age` flag on `filter_results` instead of being silently dropped. Backfilled the live DB's Greenhouse dates from already-stored `raw_json` (free, no re-fetch) and re-ran Filter fresh: 117 → 12 passing under the corrected rule (11 confirmed-fresh + 1 flagged unverified-age). `low_confidence_age` is now surfaced in the dashboard too (both `get_tailored_postings` and `get_review_list_postings` LEFT JOIN `filter_results` for it), rendered as a `⚠ unverified posting date` caveat next to any flagged posting -- visible, not hidden, same "flag it, don't silently trust or drop it" principle as Track C's own `low_confidence` marker.
  - **Location**: a strict "New York, NY" substring match would have missed most genuinely-NYC postings -- Greenhouse spells the state out ("New York, New York, United States"), Ashby/Workday often give just the bare city ("New York") with no state at all. Confirmed with you before broadening: now splits multi-location strings on `;` and matches if any entry's city (the text before its first comma) is exactly "New York" -- this also correctly rejects state-reference false positives ("Albany, New York") and treats a posting listing "New York, NY" alongside a separate "Remote" entry as a real NYC opportunity, not a remote-only one (found 29 real postings shaped exactly like that).
  - **Employment type**: only Ashby (982/982) and LinkedIn (50/50) postings carry a structured `employmentType` field live; Greenhouse and Workday's list endpoints expose none at all (0/5833, 0/23) -- defaulting those to "excluded" would have gutted most of Track A for a data-availability reason, not a real employment-type mismatch. Uses the structured field when present, falls back to a title keyword heuristic (catches "... Intern", "... Contract", etc.) when absent, and only then defaults to full-time.
  - **Title**: matches a keyword set scoped to what was asked (Software Engineer/SWE/Software Developer/Backend/Full Stack/Frontend/AI Engineer/Machine Learning Engineer + close variants), word-boundary matched so short tokens like "swe" can't false-positive inside unrelated words ("answered"). Excludes Senior/Sr./Staff/Principal/Manager, plus Lead -- added after reviewing real results showed ~18% of what passed was "Lead Software Engineer"-type titles (mostly Capital One), which reads as senior-tier in practice and is out of scope at ~22 months of experience. Also picked up narrow AI/ML-signal additions after reviewing 25 excluded Data/Research Engineer postings: Deep Learning Engineer, Deep Learning Research Engineer, and bare "Research Engineer" (HRT/Jump Trading-style research-engineer roles skew quant/ML even without the literal word "AI", and this phrase alone also covers "AI Research Engineer" and "Machine Learning Research Engineer" as substrings). Deliberately did NOT add bare "Data Engineer" -- reviewed samples showed it pulls in far more data-infra/pipeline noise (Point72's Data Engineer cluster, Stripe's "Data Analyst") than real ML matches; verified live that Point72's Data Engineer roles stayed excluded after the change while their "Research Engineer, Knowledge Graph Intelligence" role correctly started passing.
  - **Dedup**: a `filter_results` table (posting_id PK) records pass/fail + reason per posting; a posting already in it, passed or excluded, is never re-evaluated.

- Review Dashboard — done, live-verified: `src/dashboard/{store,digest}.py` + `run_digest.py` + `set_application_status.py`. No new schema and no LLM calls -- pure query + render over what every earlier stage already computed, into one combined `data/dashboard.md`:
